# SoundCIT — план развития

Состояние на 26.07.2026: мод работает и проверен вживую (Android/arm64, NeoForge 21.1.244, реальный
звук), автотест из четырёх сценариев зелёный, 45 семантических триггеров, опциональный серверный
компонент.

Ниже — что имеет смысл делать дальше, с честной оценкой сложности и рисков. Пункты внутри
направлений отсортированы по соотношению «польза / трудозатраты».

---

## A. Расширение возможностей паков

### A1. Матчинг не только по имени — паритет с OptiFine CIT
**Польза: высокая. Сложность: средняя.**

Сейчас поддерживается единственный критерий — `custom_name`. Поле `match` в правилах уже заложено
под расширение, а `SoundRule.parse` бросает понятную ошибку на неизвестном значении, так что
формат готов к росту без ломки совместимости.

Что добавить:
- `enchantment` — по наличию и уровню чар (`minecraft:sharpness>=4`);
- `damage` / `damage_percent` — по износу, как в CIT (звук треснувшего инструмента);
- `component` — по произвольному компоненту предмета 1.21 (`minecraft:custom_data`, лор, модель);
- `tag` — по тегу предмета (`#minecraft:swords`), чтобы одно правило покрывало класс оружия;
- логические связки: массив условий с `all` / `any`.

**Важное следствие для сервера.** Сейчас серверная часть шлёт подсказку только для предметов с
кастомным именем — это отсекает 99.9% трафика. С новыми критериями сервер перестанет понимать, что
именно интересно клиенту. Решение уже продумано: добавить serverbound-пакет «интересы», где клиент
один раз при входе сообщает, какие признаки ему важны. Без этого трафик вырастет непредсказуемо.

### A2. Варианты звука и параметры прямо в правиле
**Польза: средняя. Сложность: низкая.**

Сейчас значение в `sounds` — один id. Дать список с весами, а также `volume` и `pitch`:

```json
"hit": { "sounds": ["pack:hit1", "pack:hit2"], "volume": 1.2, "pitch": [0.9, 1.1] }
```

Формально это делается и через `sounds.json` ресурспака, но в правиле удобнее и позволяет менять
громкость, не трогая исходники звука. Обратную совместимость сохранить: строка = сокращённая запись.

### A3. Пользовательские таблицы триггеров
**Польза: средняя. Сложность: низкая.**

`TriggerSounds` — статическая таблица в Java. Вынести её в ресурс
(`assets/soundcit/soundcit_triggers.json`) с встроенным дефолтом, чтобы авторы паков могли
описывать свои группы звуков, в том числе для **моддовых** предметов, не дожидаясь правки мода.

Заодно снять жёсткую привязку к namespace `minecraft` в точных совпадениях: сейчас семейства
(`block.*.break`) namespace-агностичны, а точные id — нет.

### A4. Звуки, которых пока нет в словаре
**Польза: низкая-средняя. Сложность: низкая.**

Не покрыты: тыква/улей ножницами как отдельный триггер, поводок и седло, лодка и вагонетка,
книжная полка, компас на лодестоуне (частично в `use`), звук выброса предмета, звуки зачарований
кроме грома трезубца (Soul Speed, Wind Burst). Добавляются по одной строке в таблицу, но каждый
требует проверки, что резолвер до них дотягивается.

## B. Версии и загрузчики

### B1. Структура для нескольких загрузчиков
**Польза: высокая, если планируется публикация. Сложность: средняя.**

Ключевой факт: **23 файла из 31 (74%) не содержат ни одного импорта NeoForge.** Загрузчик-зависимы
только восемь:

| Файл | Что именно завязано |
|---|---|
| `SoundCIT.java`, `client/SoundCITClient.java` | точки входа `@Mod` |
| `client/ActionHooks.java`, `server/ServerActionHooks.java` | подписки на события NeoForge |
| `client/SoundReplacementHandler.java` | `PlaySoundEvent` |
| `network/SoundCitNetwork.java` | регистрация payload |
| `client/ClientCommands.java` | `RegisterClientCommandsEvent` |
| `client/AutoTest.java` | `ClientTickEvent` (только тесты) |

Вся содержательная часть — резолвер, миксины, конфиг, таблицы, сеть-формат — уже переносима как
есть. Разумно разделить проект на `common` + `neoforge` (+ позже `fabric`), пока это дёшево.

### B2. Порт на Fabric
**Польза: высокая (аудитория). Сложность: средняя.**

Что придётся заменить:
- `PlaySoundEvent` → собственный миксин на `SoundEngine.play`. У нас уже четыре миксина, пятый
  ничего не усложнит, зато **уберёт последнюю зависимость ядра от NeoForge**;
- события действий → Fabric API (`ClientTickEvents`, `UseItemCallback`, `AttackEntityCallback`) плюс
  миксины там, где у Fabric нет аналога (их меньше, чем кажется: половина наших хуков — это
  предсказание, которое можно заменить теми же funnel-миксинами);
- сеть → `ClientPlayNetworking` / `ServerPlayNetworking` с тем же форматом пакета;
- команды → `ClientCommandRegistrationCallback`.

Формат правил и паки останутся **полностью совместимыми** между загрузчиками — это главное, что
нужно сохранить.

### B3. Новые версии Minecraft
**Польза: высокая. Сложность: от средней до высокой, требует проверки.**

Риски, которые надо проверять по исходникам целевой версии, а не предполагать:
- приватный funnel `ClientLevel.playSound(double,...)`, на котором держится весь захват контекста —
  Mojang может его отрефакторить. Миксины уже написаны так, что при неудачном применении мод
  деградирует, а не падает, но покрытие просядет;
- в 1.21.2+ заметно менялись компоненты предметов и слоты экипировки;
- id звуков между версиями добавляются и переименовываются — таблицу триггеров нужно сверять
  заново, иначе документация начнёт врать.

Пункт A3 (таблицы в ресурсах) сильно облегчает поддержку версий: часть различий можно будет
описать данными, а не кодом.

## C. Серверная часть

### C1. Плагин для Paper/Spigot
**Польза: высокая для многопользовательской игры. Сложность: высокая, есть неизвестные.**

Протокол уже спроектирован под это: сервер сообщает **причину** звука, а не замену, пакет
версионирован и помечен `optional`. То есть отправителем может быть не только мод, но и плагин —
для клиента это просто plugin message на канале `soundcit:sound_cause`.

Главная неизвестность, которую надо проверить прежде всего: **Bukkit API не даёт доступа к seed
звука**, а именно seed служит ключом сопоставления. Скорее всего понадобится перехват исходящих
`ClientboundSoundPacket` через packetevents или ProtocolLib. Пока это не проверено, оценивать сроки
нельзя.

Запасной вариант: если seed недостижим, ввести для плагинов режим сопоставления по «звук + позиция +
окно времени» — менее точный, но работающий; клиентская часть под это уже готова, там есть слой
позиционной эвристики.

### C2. Прокси-режим (Velocity/BungeeCord)
**Польза: низкая. Сложность: средняя.** Имеет смысл только если появится C1.

## D. Качество, отладка, публикация

### D1. Экранная отладка вместо чтения логов
**Польза: средняя. Сложность: низкая.**

`/soundcit why` уже показывает журнал, но авторам паков удобнее оверлей: последние звуки, их id,
подменён/нет и каким слоем. По сути это вывод существующего журнала в HUD.

### D2. Расширение автотестов
**Польза: средняя. Сложность: низкая.**

Сейчас четыре сценария. Не покрыты: загрузка правил **из настоящего ресурспака** (а не из ассетов
мода) — это до сих пор не проверялось запуском; F3+T; поведение при неоднозначности (два игрока
рядом с одинаковыми предметами); работа на ванильном сервере (клиент с модом, сервер без).

### D3. Публикация
**Польза: зависит от намерений. Сложность: низкая.**

Нужны: английская документация (в работе), лицензия, иконка мода, страница на Modrinth/CurseForge,
`updateJSONURL` в `neoforge.mods.toml` для проверки обновлений.

## Предлагаемый порядок

1. **Доделать документацию и пример-пак** (уже начато) — без этого мод бесполезен для чужих людей.
2. **D2: проверить загрузку правил из ресурспака.** Это дыра в тестах: весь пользовательский
   сценарий держится на непроверенном пути.
3. **A3 + A2** — дешёвые улучшения, которые сразу расширяют выразительность паков и заодно готовят
   почву для поддержки версий.
4. **B1** — разделить на common/neoforge, пока проект маленький и это дёшево.
5. **A1** — матчинг по чарам, износу и компонентам: самое заметное расширение возможностей.
6. **B2** — Fabric.
7. **C1** — плагин, начиная с исследования вопроса про seed.

Пункты 1–2 стоит делать в любом случае; порядок дальше зависит от того, что важнее — глубина
возможностей (A) или охват аудитории (B).
